# 安全稽核 2026-10

- 日期：2026-10-14（`https://dev-in.tw` 上線當天）
- 範圍：`apps/api`、`apps/web`（法務頁面除外）、`packages/dns`、`packages/contract`、Dockerfile、GitHub Actions、
  Dependabot、`pnpm-workspace.yaml`。威脅模型見 [`THREAT_MODEL.md`](THREAT_MODEL.md)。
- 方法：逐檔閱讀安全關鍵路徑（認證、授權、CSRF、輸入驗證、DNS 同步、外部呼叫、日誌、標頭、SSE、限流），
  另外做了三個實際驗證（見 §2 最後）：以真正的 `createApp`（memory provider + 拋棄式 PostgreSQL 18）在
  headless Chromium 開 `/api/docs`；用 Turnstile 的測試 sitekey 在新標頭下實際載入 Turnstile；以唯讀檔案系統
  啟動 Next standalone。`pnpm audit`（prod 與全部）0 個已知漏洞。
- 分支：`security/hardening`。合約（`packages/contract`）沒有任何變更；新行為只使用既有錯誤碼
  （`VALIDATION_FAILED`、`RATE_LIMITED`、`RECORD_TARGET_NOT_ALLOWED`），都在合約的 `IMPLICIT_ERRORS`
  或端點原本的錯誤清單內，因此不需要在 PLAN.md 的合約變更紀錄加列。

嚴重度依「可利用性 × 對 dev-in.tw 與使用者的實際影響」判定，不是單純的 CVSS。

## 2. 確認無問題的控制

以下項目逐一檢查過，沒有發現問題（多數已有測試）：

- **GitHub OAuth**：`state` 32 bytes 亂數並以 `timingSafeEqual` 比對、PKCE S256、HMAC 簽章且 10 分鐘到期的
  `__Host-dit_oauth`、scope 只有 `user:email`、access token 用完即丟、停權帳號拒絕登入、`redirect` 兩端都驗證。
- **Session**：只存 SHA-256、token 32 bytes、idle 14 天 / absolute 60 天、登出與裝置撤銷是 server 端撤銷。
- **CSRF**：Origin 完全比對、`Sec-Fetch-Site: same-site` 也拒絕、body 只接受 JSON，dev 登入在 production 拒絕啟動。
- **授權**：子網域、紀錄、轉移、session 撤銷都以擁有者限定，越權一律 404；admin 端點非 admin 回 404；
  `adminUpdateUser` 不能改角色、不能停權自己。
- **轉移競態**：轉移列與子網域列 `FOR UPDATE`，接受前重新檢查狀態、擁有者與配額；與釋出同時發生時由資料庫的死結偵測中止其中一個，不會出現不一致。
- **輸入驗證**：A / AAAA 公網檢查涵蓋 PLAN §3.9 全部網段且 IPv6 限 `2000::/3`；TXT 1–2,048 可列印 ASCII、
  每名稱 5 筆；MX / SRV / CAA 欄位範圍；SRV 名稱格式；CAA flags 與 tag 白名單；不開放 NS 與 proxied；
  子網域名稱禁止 `--`（含 `xn--`）與 1–2 字元。
- **DNS worker 安全閥**：只動有 `dit:` 標記的紀錄、`SYSTEM_RECORD_NAMES` 對帳時略過、大量刪除煞車、
  啟動時比對 zone 名稱、`DNS_PROVIDER=cloudflare` 不可與 dev 登入並用。
- **SSRF**：所有對外請求都是固定主機（Cloudflare API、GitHub、Turnstile、四個 DoH resolver、Discord webhook）；
  Next 沒有設定 `images.remotePatterns`。
- **Client IP**：沒有 Cloudflare 時採用 Traefik 附加的 `X-Forwarded-For` 最右邊一個；有 Cloudflare 時只在來源屬於
  Cloudflare 才採信 `CF-Connecting-IP`；兩種模式都已有測試。
- **錯誤與日誌**：5xx 只回通用訊息；Cloudflare / GitHub 的錯誤原文不外傳；wide log 不含 cookie、token、OAuth code、
  完整 email，只記 IP 的加鹽雜湊；postgres.js 的錯誤不會帶出查詢參數。
- **DNS wire 解析**：壓縮指標有迴圈上限。
- **供應鏈**：lockfile、`minimumReleaseAge: 4320`、`onlyBuiltDependencies: []`、Dependabot（npm、actions、docker）
  都有 3 天 cooldown；`pnpm audit` 0 個已知漏洞。
- **映像**：兩個映像都以 `node` 執行並有 HEALTHCHECK。API 不寫入任何檔案，可以用唯讀根目錄；web 以唯讀複本實測，
  只有 `.next/cache`（圖片快取）需要可寫，映像已預先建立該目錄。

**手動驗證紀錄**

- `/api/docs`：以真正的 `createApp`（含完整的中介層與標頭）在 headless Chromium 開啟：`self.origin` 是 `"null"`、
  API 文件完整顯示、沒有 console 錯誤；在同一個瀏覽器先以 dev 登入取得 admin session，再從 docs 頁面內
  `fetch("/api/v1/me", { credentials: "include" })` 與 `POST /api/v1/auth/logout` 都被瀏覽器擋下（CORS），
  `document.cookie` 丟出 `SecurityError`，事後 session 仍然有效。沒有記憶體 storage shim 時 Scalar 會因為
  sandbox 裡不能用 `localStorage` 而無法初始化，這是加 shim 的原因。
- Turnstile：e2e 用的是 mock 的假驗證框，所以另外用 Cloudflare 的測試 sitekey（`1x00000000000000000000AA`）在新的
  Permissions-Policy 與 COOP 下開 `/report`：Turnstile iframe 正常載入並產生 token，沒有 permissions-policy 違規。
  正式 sitekey 會跑真正的挑戰，上線後請實際送出一次申請或檢舉確認。
- 唯讀檔案系統：把 Next standalone 複製後 `chmod -R a-w` 啟動，首頁、文件、狀態、登入、OG 圖片、`/_next/image`
  都正常回應，唯一的錯誤是寫入 `.next/cache` 失敗。

## 3. 新增的防護（摘要）

- API：32 KiB body 上限；`default-src 'none'` CSP、COOP、HSTS（無 `includeSubDomains` / `preload`）；
  `/api/docs` CSP sandbox + 固定版本 + 記憶體 Web Storage shim；IPv6 /64 限流與 bucket 上限；每請求重算 admin 角色；
  重複 cookie 視為無效；登入時撤銷舊 session；SSE 名額（使用者 / IP / 全域）與每分鐘 session 重新驗證；
  轉移邀請限流；系統名稱硬保留；每輪對帳匯入 zone 名稱；健康檢查合併 DB 查詢；dangling CNAME 偵測。
- `packages/dns`：特殊用途網域目標、`xn--` 紀錄名稱、`wpad` / `isatap` / `mta-sts` 保留。
- Web：登入轉址驗證與 API 一致；COOP、CORP、`X-DNS-Prefetch-Control`、更完整的 Permissions-Policy。
- Repo：`SECURITY.md`、CodeQL、`pnpm audit` job、base image digest、runtime 移除套件管理工具。

## 5. 需要在程式碼之外處理的事項

依建議的優先順序排列。

1. **GitHub repo 設定（Dev-in-tw/dev-in.tw）**
   - Settings → Code security：開啟 *Secret scanning*、*Push protection*、*Private vulnerability reporting*、
     *Dependabot alerts* 與 *Dependabot security updates*。
   - CodeQL：這次加的是 advanced setup（`.github/workflows/codeql.yml`）。如果 repo 已經開了 *Default setup*，
     要先關掉，否則 advanced workflow 上傳結果時會被拒絕。
   - Rules → Rulesets（`main`）：禁止 force push 與刪除；必須透過 PR；required status checks 設為
     `Lint, typecheck, test, build`、`api (postgres 18, image)`、`web e2e and image`、`Dependency audit (prod, high+)`、
     `Analyze (javascript-typescript)`；至少 1 個 review（若人手允許）；不要開 *Require linear history*
     （專案規定用 `git merge`）。
   - `Dependency audit` 設為 required 時要注意和 `minimumReleaseAge: 4320` 的交互作用：某個相依套件出現 high 漏洞、
     而修補版發佈未滿三天時，`main` 上的 audit 會變紅、所有 PR 都被擋，連修補 PR 本身也裝不到修補版。解法是在修補 PR
     的 `pnpm-workspace.yaml` 暫時加上 `minimumReleaseAgeExclude: [<套件名>]`（pnpm 10.32 支援），讓修補版立刻能裝，
     三天後再移除；真的沒有修補版時，才用 `auditConfig.ignoreGhsas: [GHSA-…]` 暫時忽略該筆並註明移除日期。
     如果不想承擔這個流程，就把 audit 設為非 required，改看 Dependabot alerts。
   - Settings → Actions：*Workflow permissions* 設為 read-only；*Require approval for all outside collaborators*；
     *Allow actions* 限定為 GitHub、已驗證的建立者與 `pnpm/action-setup`、`docker/*`。
   - 把 `ci.yml` 既有 job 的 actions 也改成 SHA（WP0 的檔案，這次沒動），Dependabot 會自動維護。
   - 管理員（HACO8888）與 org 成員必須啟用 2FA（建議 passkey）；可在 org 設定強制 2FA。
2. **Cloudflare（仍在代理後面時）**
   - SSL/TLS 設為 *Full (strict)*、*Always Use HTTPS*、*Minimum TLS 1.2*。
   - 不要在 Cloudflare 的 HSTS 設定勾 *Include subdomains* 或 *Preload*（應用程式已送 HSTS）。
   - 關閉 *Rocket Loader*、*Email Address Obfuscation*、*Automatic HTTPS Rewrites* 之類會改寫 HTML 或注入腳本的功能，
     它們會和 nonce CSP 衝突。
   - 原點保護：開啟 **Authenticated Origin Pulls**，在 Traefik 的 `dev-in.tw` router 要求 Cloudflare 的 client
     certificate（`tls.options` 的 `clientAuth`，`RequireAndVerifyClientCert`）。只用防火牆限定 Cloudflare IP 不夠，
     其他 Cloudflare 租戶也能從 Cloudflare IP 連進來。
   - WAF rate limiting：`/api/v1/auth/*` 每 IP 每分鐘 30 次、`/api/v1/reports` 每 IP 每小時 20 次，作為應用層之外的第二層。
   - API token：只給 `Zone:DNS:Edit` + `Zone:Read`、只限 `dev-in.tw`，開啟 *Client IP Address Filtering*（Dokploy
     主機出口 IP），設定到期日並每年輪替。
   - Turnstile widget 的 *Hostname management* 只留 `dev-in.tw`。
   - 開啟 Cloudflare 的通知：DNS 紀錄變更、API token 即將到期、Origin 錯誤率。
3. **搬到 Lazco 自建 DNS、不再有 Cloudflare 代理時**
   - Dokploy 的 api 環境變數改成 `TRUST_CLOUDFLARE=false`（程式在沒有 Cloudflare 時已會自動不採信
     `CF-Connecting-IP`，這是收斂設定）；`TRUSTED_PROXY_HOPS` 維持 `1`。
   - Traefik 維持不信任外部 forwarded headers（不要設 `forwardedHeaders.insecure` 或 `trustedIPs`）。
   - 在 Traefik 加一層限流與 body 上限：`ratelimit` middleware（例如 `average: 20`、`burst: 50`，以 `ipStrategy.depth: 0`）
     與 `buffering` middleware（`maxRequestBodyBytes: 65536`）掛在 `dev-in.tw/api` router。
   - 量體型 DDoS 沒有 Cloudflare 擋，評估 CrowdSec bouncer 或上游清洗。
   - 要寫新的 `DnsProvider` adapter（ADR-0005），並先在 staging zone 驗證大量刪除煞車。
   - DNSSEC 見第 6 項，**切換 NS 前**一定要先處理 DS。
4. **Traefik / Dokploy**
   - 不要對主機 publish web 的 3000 與 api 的 3001（威脅模型 §6 的假設 1）。
   - Access log：callback 的 query string 含 OAuth `code` 與 `state`。把 access log 的 `RequestPath` 欄位設為 `drop`
     或縮短保存期限（例如 7 天），Cloudflare Logs 若有開也比照。
   - `entryPoints.websecure.transport.respondingTimeouts.readTimeout` 設 30–60 秒，避免慢速連線佔住資源。
5. **容器執行設定（Dokploy → Advanced / Swarm）**
   - api：`read_only: true`、`cap_drop: [ALL]`、`security_opt: [no-new-privileges:true]`、tmpfs `/tmp`。
   - web：同上，另外 tmpfs 掛在 `/app/apps/web/.next/cache`（大小 64 MB 即可）。
   - 維持記憶體上限（api 192 MB、web 320 MB）。
6. **DNSSEC**
   - 現在：Cloudflare → DNS → Settings → *Enable DNSSEC*，把產生的 DS 紀錄交給 `.tw` 註冊商（TWNIC 受理註冊商）。
   - 搬家時：DS 指著 Cloudflare 的金鑰時直接換 NS，整個網域會驗證失敗。做法二選一：
     (a) 先在註冊商移除 DS，等舊 DS 的 TTL（至少 2 天）過後再換 NS，新 DNS 上線並簽章後再登錄新的 DS；
     (b) 用 multi-signer（RFC 8901）讓兩邊的 DNSKEY 同時存在再切換。
7. **CAA**
   - **不要在 apex 設限制性的 `issue`**：CAA 會往上找，apex 的 CAA 會套用到所有沒有自己 CAA 的使用者子網域，
     而使用者的平台不一定用 Let's Encrypt（例如 Cloudflare Pages 會用 Google Trust Services 或 SSL.com）。
   - 主站自己的憑證改用 Certificate Transparency 監控（例如 Cert Spotter 或 crt.sh 訂閱 `dev-in.tw`、`www.dev-in.tw`）。
   - 使用者需要時可以在自己的子網域加 CAA（已開放此類型）。
8. **Public Suffix List**
   - 到 [publicsuffix/list](https://github.com/publicsuffix/list) 開 PR，把 `dev-in.tw` 加到 PRIVATE 區段，
     並在 zone 加 `_psl.dev-in.tw TXT "https://github.com/publicsuffix/list/pull/<編號>"`（`_psl` 已在
     `SYSTEM_RECORD_NAMES`）。PSL 要求網域到期日至少還有 2 年，先確認續約。
   - 收錄並隨瀏覽器發佈後（通常數個月），使用者子網域彼此與主站就是不同 site：cookie bombing 與 SameSite 的問題消失，
     Let's Encrypt 的額度也改成每個子網域各自計算。
9. **Email 與網域信譽**
   - `dev-in.tw` 的 DMARC 用 `p=reject; sp=none`（或明確的 `sp=`）：沒有 `sp` 時子網域會繼承 `p=reject`，
     使用者從自己的子網域寄信會被拒。SPF 與 DKIM 只涵蓋 apex 寄信的服務。
   - 確認 `security@`、`abuse@`、`hello@` 都能收信（`security@` 轉寄 `contact@lazco.tw`），並測試一次。
   - 定期以 Google Safe Browsing / URLhaus 查詢 `dev-in.tw` 底下的名稱（PLAN §3.10 的 P2）。
10. **監控與告警**
    - 在 Infisical 設 `DISCORD_WEBHOOK_URL`：對帳煞車、dead job、Cloudflare 認證失敗、zone 使用量、新檢舉、
      待審子網域、dangling CNAME 都會送到這裡。
    - 外部 uptime 監控 `https://dev-in.tw/api/readyz` 與 `https://dev-in.tw/healthz`。
    - 從 Dokploy 的 log 對 `status >= 500` 比例、`rate_limited` 激增與 `error_code: CSRF_REJECTED` 激增設告警。
    - PostgreSQL 備份每月實際還原一次，並在還原後跑對帳確認大量刪除煞車有擋下（不要用 `force`）。
11. **機密管理**
    - 依 PLAN §3.14 確認舊系統的金鑰都已輪替；之後 `SESSION_SECRET`、GitHub client secret、Cloudflare token、
      Turnstile secret、`REPORT_IP_SALT` 每年輪替一次（輪替 `SESSION_SECRET` 只會讓進行中的登入流程失效，
      不影響既有 session）。
    - Infisical 給 Dokploy 的 machine identity 只開 `Dev-in.tw` 專案的 production 環境唯讀。
